# 地图实体同步重构方案（Marker、MarkerLink、Item）

团队评审稿 · 2026-11-21 · 适用于地图首屏、自动更新、本地缓存、编辑与删除。第一阶段由前端在现有接口上实施，第二阶段由前端与 Java、Rust 后端共同落地。

| 阶段 | 交付结果 | 发布门槛 |
| --- | --- | --- |
| 第一阶段 · 前端缓解 | 空库从归档建立基线，热库复用分片。三类实体经同一入口提交到 IndexedDB，地图和管理页消费已提交的结果 | 首登不再按全部点位 ID 回查详情。关联全量导入不触发全体端点回查。中断、迟到响应和回读失败有明确的恢复路径 |
| 第二阶段 · 后端治根 | 服务端提供同一时点的快照、可重放的事务日志和幂等命令。前端从持久化游标追赶 | 丢弃全部 WebSocket 提醒后，三类实体仍与同一服务端游标的状态一致。创建响应丢失后用原命令重试，只产生一个 ID |

## 现状与代码依据

| 路径 | 当前行为 | 用户可见的影响 |
| --- | --- | --- |
| Marker 首登 | 默认读本地表，再取全部 `id/version/linkageId` 比对快照。空库会将几乎所有 ID 送去详情查询，每批 100、并发 4。[Marker store](../src/stores/marker.ts) · [diff](../src/stores/utils/diffMarkers.ts) | N 个点位约需 `⌈N/100⌉` 次详情请求，另有快照请求。完整二进制拉取只在全量分支，MD5 页未参与启动 |
| Item 初始化与对账 | `init` 联网扫区，随后的 `diff` 再扫一轮。每区只取第一页 500 条，未检查 `allSettled` 中的失败。`full` 与 `diff` 都只合并返回记录。[Item store](../src/stores/item.ts) | 漏收的删除留下旧物品，超过第一页的物品可能缺失。点位渲染依赖首项物品，缺失会使点位在地图上消失 |
| MarkerLink 刷新 | `diff` 和 `full` 均遍历全表，再回查整批边涉及的端点。合法空表在 `clear` 前提前返回。同组换边时图层可能因组 ID 集合相同而跳过刷新。[关联 store](../src/stores/markerLink.ts) · [连线图层](../src/hooks/useMapLayers/useLinkLayer.ts) | 首登与 Marker 同步重复读同一批点位。旧边可能留在磁盘、内存或地图上 |
| 并发写入与删除 | Manager 先改内存，再将原始批次传给 Worker 写盘。CRUD 和 WS 多处只更新内存。删除事件已携带 ID，仍要等历史查询和解析成功才发给 store。[Manager](../src/stores/hooks/useManager.ts) · [写盘](../src/stores/utils/bulkWrite.ts) · [WS 事件转换](../src/stores/socket/hooks/useAppEvent.ts) | 即便内存拒绝了旧版本，原始记录仍可能落盘。历史查询失败会漏删，早发晚到的详情响应会在删除后重新插入实体 |
| 创建与回读 | 创建接口返回新 ID 后，store 再回读详情。第二步出错会使表单提示新增失败并释放已有的提交锁。[创建入口](../src/components/MarkerModifyer/hooks/useMarkerCreate.ts) · [Marker store](../src/stores/marker.ts) | 用户重试可能创建第二个点位。另一种重复来自两名用户在陈旧地图上分别提交，两者需要不同的处置 |
| 连接与视图 | Socket 重连只上报连接状态，DedicatedWorker 回退未注册完整的连接处理。点位管理页筛选缓存仅用查询条件作键。[Socket Worker](../src/worker/webSocket/socket.worker.ts) · [点位管理页](../src/pages/pageMarkerManager/hooks/useMarkerList.ts) | 显示已连接时仍可能缺少断线期间的变更。即使 store 已更新，管理页仍可能命中旧结果 |

## 第一阶段 · 前端缓解

保留 Pinia 对外的 `markerList`、`itemIdMap`、`groupIdMap` 和手动 `update()`。分片用于复用下载和断点续传。筛选、计数、点位存在性判断和跨页连线继续读取当前作用域的完整已提交数据。尚无完整基线时，界面展示加载状态。

### 按本地基线选择数据源

| 资源 | 空库、缓存损坏或格式升级 | 已有完整基线 | 接口降级 |
| --- | --- | --- | --- |
| Marker | 取 `marker_doc.listMarkerBinaryMD5` 清单，通过 `listPageMarkerByBinary({md5})` 限流下载缺页。归档就绪后用在线 diff 补发布后的增删改及 `linkageId` 变化 | 先展示缓存。小差异复用现有批量回读；大差异按缺页字节数、预计详情批次数和实测耗时选择归档页或整包，再核对在线变化 | 分页契约未验证或不可用时，用已有 `listMarkersByBinary` 完整二进制接口建基线 |
| Item | 取 `item_doc.listItemBinaryMD5` 清单，通过 `listPageItemByBinary({md5})` 建立完整基线 | 只下载变化页，收到涉及具体物品的通知时按 ID 回源。归档滞后或漏收通知时，用在线地区分页轮转核对 | `listItemIdByType` 按地区限流、按 `total` 翻完，每轮每区只遍历一次。失败、重复页或记录不足的地区保持待核对 |
| MarkerLink | 取 `marker_link_doc.listAllMarkerLinkageBinaryMD5` **整表摘要**及 `listAllMarkerLinkageBinary` 列表包。首次导入使用 Marker 基线中的端点 | 摘要相同且没有待核对组时复用本地数据。已知变动按新旧组回源，未知范围的变动做整表核对 | 列表包未验证或不可用时，用一次 `getMarkerLinkageList({isTraverse:true})` 拉全。按组回读使用 `groupIds` |

以上为接口语义，调用时遵循生成客户端的 `pathParams` 和 `data` 签名。现有 MD5 清单元素只声明 `md5/time`；Marker 全包和 diff 已有自定义解码器。接入前用两套后端的样本分别验证压缩容器、编码、摘要对应的字节、刷新时机、可见范围和字段完整性。比对同一实体的归档与详情，覆盖安全整数 ID、`version`、`linkageId`、`hiddenFlag`、物品引用和渲染字段。只有通过样本对照的归档才能用于对应范围的启动。[归档路由](../src/api/alova/apiDefinitions.ts) · [摘要类型](../src/api/alova/globals.d.ts) · [已有解码器](../src/api/alova/index.ts)

### 安装归档与恢复中断

1. 在现有 Dexie `AppData` 中记录作用域、格式版本、生效清单、已验证页、每页成员 ID 和上次成功核对时间。作用域区分后端实例、账号和可见权限。迁移时仅将归属及完整性可确认的旧表作为基线，保留 `userArchive` 等用户数据。[数据库定义](../src/database/db/app.ts)
2. 将新清单和新页写入暂存区。复用同一作用域和格式下已验证的内容，校验、解码和成员检查成功后标记该页完整。失败可续传，页面仍读取上一份完整数据。限制下载、解码和写盘的并发，避免三个 store 各自占满资源。
3. 所有页齐备后复核清单；对固定 URL 的关联整包还要核对正文与摘要是否匹配。归档发生变化时复用仍然命中的页，重新准备其余部分。先分别汇总新、旧清单中所有页的成员，再计算**旧集合减新集合**，处理跨页迁移。单页消失只能说明归档成员变化，在线已确认的新增、修改和删除仍须保留。
4. 通过统一提交入口切换生效批次，并重放下载期间已确认的本地变化。下载时间不能给旧归档赋予更高版本。MD5 相同只表明归档内容相同；对发布后发生的在线修改保留失效标记，直到在线核对完成。界面分别记录归档时间、最近核对时间和待核对范围。

### 统一提交、排序与多标签页

同一作用域设置一个同步协调器。启动、手动刷新、CRUD 回执、WS 提醒、`MarkerBinaryPurged`、`ItemBinaryPurged`、`MarkerLinkageBinaryPurged`、回到前台、网络恢复、Socket 重连及低频定时对账统一入队。运行期间合并重复请求，保留新到达的 ID、组和刷新原因，当前轮结束后继续处理。

| 存储内容 | 写入与读取规则 |
| --- | --- |
| 已确认实体与 Pinia 投影 | 在提交入口校验版本、轮次和作用域，生成**实际接受**的增删集合。将该集合、删除记录、待核对项及元数据写入同一事务。事务成功后用同一集合更新 Map、通知图层。写盘错误向上传递，下次从最后一次成功提交恢复 |
| 删除记录（墓碑） | 按作用域、资源和 ID 持久化。删除通知到达时即依据消息里的实体 ID 登记，历史和操作者查询独立用于通知展示。迟到的旧详情和旧归档均受墓碑保护 |
| 待确认命令与草稿 | 与归档页分表保存提交标识、状态、已知结果 ID 和草稿。如果展示尚未确认的编辑，只叠加用户触碰的字段。标明待确认状态，避免覆盖其他人已提交的字段 |
| 暂存页与同步元数据 | 记录已验证成员、生效批次、本地变更代数、最近成功和失败信息。仅在对应范围完整时计算删除。合法空表、合法空组可以清空旧数据；缺字段、少返回 ID 或分页失败进入待核对队列 |

每次异步查询捕获作用域、轮次和相关实体的本地变更代数。提交时再次检查：低版本丢弃，查询期间已修改的实体重新核对。特别是关联操作可能只改 `linkageId` 而不提高 Marker 的 `version`，此时要校验关联修改代数，避免旧 diff 就地改掉新对象。第一阶段能识别客户端已观察到的次序；断线期间服务端事务的先后顺序留给第二阶段协议表达。

同一作用域使用 Web Locks 或带事务校验的租约选出写入者，其他标签页订阅已提交批次，重新成为写入者时从数据库恢复。作用域、锁和广播通道一起切换，拒绝旧账号的在途结果。修复 DedicatedWorker 的 `open`、`close`、心跳和消息处理，在 token 刷新时更新握手凭证或重连。页面分别显示连接状态、最近成功核对时间、同步中、离线和同步失败。

### CRUD 与地图视图

- **Marker 创建。** 提交前保存本次命令标识。取得 `markerId` 后即显示“已创建，详情同步中”，回读失败只按该 ID 重试。若 POST 超时且没有 ID，则显示“结果待确认”，保留草稿及核对入口，禁止自动重发创建。缓存陈旧时优先核对邻近候选，减少两人重复打点的窗口。
- **MarkerLink 修改。** 从原始 `MarkerLinked` 载荷保留 `groups` 和端点 ID，与操作前的旧组、删除边及新组合并。对明确完整的组做整组替换，覆盖解散、拆组、并组、同组换边。仅补读发生变化且未被 Marker 同步覆盖的端点；关联边与受影响 Marker 准备好后一起发布。回读失败的组保留待核对状态。图层订阅组内容修订号。
- **Item 与派生视图。** WS、命令回读和分页结果均走版本检查，批量回读消费所有实体。物品跨区移动须同时核对旧区与新区。删除、移动、类型变化或补齐缺失物品时，重算引用它的 Marker。点位管理页筛选缓存加入 Marker、Item 及可见范围的修订号。地图与管理页共享已提交实体，避免数据已更新而图层或列表仍显示旧值。[点位渲染](../src/stores/utils/createRenderMarkers.ts) · [筛选缓存](../src/pages/pageMarkerManager/hooks/useMarkerList.ts)

## 第二阶段 · 后端治根

沿用第一阶段的本地提交入口。服务端给三类资源提供同一可见范围的快照和有序事务批次。WebSocket 用于降低在线延迟，客户端在启动、重连、前台恢复和定时对账时都可以独立追赶。

```mermaid
flowchart LR
    Command["创建、编辑、删除"] --> Server["业务库与事务变更日志"]
    Server --> Snapshot["分片快照与增量接口"]
    Server --> Notice["WebSocket 提醒"]
    Notice --> Sync["客户端同步协调器"]
    Snapshot --> Sync
    Sync --> DB[("IndexedDB 实体、墓碑、游标")]
    DB --> Stores["Pinia 已提交投影"]
    Stores --> UI["地图与管理页"]
```

### 快照、日志与恢复契约

以下接口为拟议契约，前后端共同确定字段与编码。`scope` 表示可见数据范围，`epoch` 表示数据流世代，`cursor` 是服务端签发的已提交位置，实体 `version` 用于业务写冲突判断。

| 契约 | 服务端保证 | 客户端行为 |
| --- | --- | --- |
| 一致性快照 | 返回 `scope、epoch、snapshotCursor、shards[]`。每个分片描述资源、稳定分片标识、内容摘要、记录数、编码与下载地址。三类资源对应同一个已提交位置，先发布不可变分片，再原子公布清单 | 空库、游标失效或完整性检查失败时下载快照。复用同一作用域的已验证分片，完整安装后持久化 `snapshotCursor`，立即从该位置补齐下载期间的变化 |
| 可重放增量 | `changes(after, limit)` 返回有序的 `batches[]、nextCursor、hasMore`。每个批次对应一个完整业务事务，含批次 ID、实体类型、ID、操作和实体载荷或删除记录。日志顺序遵循**事务提交可见顺序**。业务写与变更日志在同一数据库事务内提交 | 按返回顺序应用，跨资源批次整体生效。一个拆组事务内，旧边删除、新边建立和端点 `linkageId` 改变同时可见。分页边界落在完整事务之间 |
| 续传与重建 | 为重复请求提供可重放结果。明确日志、墓碑与快照文件保留窗口。`epoch` 改变、游标过期或无法续传时返回 `snapshotRequired`。权限收窄需发出移出记录，或使作用域世代失效 | 沿 `nextCursor` 拉取至 `hasMore=false`。权限变化立即停用旧可见范围，按服务端要求追赶或重建。同一作用域内可用约定位置的实体数、成员和摘要对账 |
| WS 提醒 | 提醒携带作用域、`epoch`、事件 ID 和可用的最新位置。变更在业务事务提交后才可读、可通知 | 合并提醒、去重通知，始终从本地已提交游标拉取。重复、乱序、漏发提醒均可由同一恢复路径处理 |

**游标与数据原子提交。** 提交前核对本地 `scope、epoch、cursor` 与请求起点；将响应覆盖的实体变化、墓碑和 `nextCursor` 写进同一个 Dexie 事务。崩溃或写盘失败时从旧游标重放，成功后才发布 Pinia 更新。相同批次重复应用保持幂等。有序删除遮住旧更新，恢复已删除实体需要显式且更晚的服务端变更。仅在完整快照覆盖旧变更且旧请求已失效后回收相应墓碑。同步中可以逐批持久化，UI 在追到本次服务端目标后才标记已追平。

### 幂等命令、编辑冲突与业务重复

1. **同一次创建的重试。** 客户端发出请求前持久化 `clientMutationId` 与载荷摘要。服务端对调用方作用域和幂等键建立唯一约束，在创建事务中写入业务实体、变更日志和命令结果。同键同载荷返回首次结果和实体 ID，同键异载荷返回冲突。明确幂等记录的保留期及结果查询方式，使其覆盖支持的客户端重试窗口。可随响应返回实体、版本和提交位置；客户端仍从自身游标追赶所有事务。
2. **并发编辑或删除。** 延续已有 Marker 旧版本拒绝行为，统一 Item、关联组、端点调整和批量操作的 `baseVersion` 或组修订号。版本匹配才能提交。冲突返回 409 及可见的最新状态；客户端保留草稿，展示差异。关联修改涉及多条边与端点时，服务端明确整笔成功或失败的事务边界。[已有版本冲突用例](../tests/api/parity/cases/10-parity-invariants.test.ts)
3. **多人独立创建同一业务点。** 不同用户各自的命令有不同幂等键。有稳定业务标识时，在业务作用域建立唯一约束；允许同坐标多层、不同物品等合法重叠时，由服务端返回同图层、同物品、邻近位置的候选及差异，供用户确认。唯一字段和距离规则需产品确认后落库。
4. **弱网与离线。** 待确认命令记录区分发送中、结果未知、已接受待同步、已确认和冲突。产品开放离线编辑时可增加持久化命令队列（Outbox），恢复联网后使用原幂等键发送。换账号时隔离队列；超过可安全重试窗口时先核实原结果。

## 实施顺序、灰度与回滚

| 顺序 | 交付与切换方式 |
| --- | --- |
| 第一阶段内 | 先记录首登请求基线，修复创建回执与删除事件处理；再接入统一提交、失败传播和写入者选举；最后按资源启用已验证的归档适配器，接通渲染与筛选失效。保留手动全量入口，便于在当前作用域重建基线 |
| 第二阶段内 | 服务端先上线事务日志、幂等命令和版本化读取接口。用只读影子客户端在相同测试数据及提交位置上比较实体 ID、版本、删除集合、组成员和可渲染点位数，再按作用域切换主同步客户端 |
| 回滚 | 第一阶段可按资源关闭归档读取，回到表中列出的完整读取方式，继续使用同一提交入口。第二阶段回滚时停止新协议写入者、隔离其游标，以第一阶段路径重新核对基线。保留未决命令，按原命令标识查结果；两个协议的写入者互斥 |

## 验收与观测

| 阶段 | 场景 | 可验证的结果 |
| --- | --- | --- |
| 一 | 空库首登、热库归档未变、仅一页改变 | 冷库的 Marker 详情请求仅覆盖归档之后的待补差异；关联全量导入额外端点回查为 0；完整热库未变时归档正文下载为 0；仅一页改变时只下载该页 |
| 一 | 页 A 的实体移到页 B、下载中断、摘要变化、损坏页、合法空关联表 | 跨页实体保留；失败或刷新后仍读取上一完整基线并可续传。明确完整的空关联表能同时清除旧磁盘记录和地图连线 |
| 一 | 某区超过 500 个 Item、分页失败、Item 跨区、同组换边 | Item 拉全；失败区域保留原数据和待核对标记。物品与关联变化在地图和管理页可见，筛选和总数随提交更新 |
| 一 | 删除历史查询失败、旧读晚到、写盘失败、多标签页切换、账号权限变化 | 通知文案失败不影响按 ID 删除；旧读不能使删除项在刷新后复活。磁盘失败不推进成功状态。旧账号的缓存和在途响应均不会进入新视图 |
| 一、二 | 收到新 ID 后详情查询失败；POST 已落库但响应丢失 | 前者仅重试回读。后者第一阶段进入待确认，第二阶段使用原键重试并返回同一 ID。两个独立用户创建时按业务查重规则处理 |
| 二 | 断网期间增删改、完全关闭 WS、长时间离线、游标过期、快照下载中拆组 | 保留窗口内从旧游标追平，超出窗口自动重建。追平后与同一游标的服务端状态逐实体、逐组一致 |
| 二 | 重复增量、同一事务跨三类资源、事务中途退出、并发提交过期版本 | 重放一次与多次结果一致；实体、墓碑和游标一同成功或回滚。重启可续传；版本冲突保留草稿且不覆盖新状态 |

第一阶段按冷库、热库和弱网分别采集首屏可用及对账完成时间 P50/P95、传输字节、分片命中率、详情批次数、关联产生的额外端点回查数、写盘失败数和最老待确认命令时长。将同一数据集、相同权限和网络条件下的新旧链路对比，依据实测成本设定 Marker 从按 ID 回读切换到归档的阈值。可扩充[现有 diff 单测](../tests/stores/diffMarkers.test.ts)和[分批回读单测](../tests/stores/fetchMarkersByIds.test.ts)，另以浏览器级测试覆盖刷新、真实 IndexedDB 和最终渲染。

第二阶段补充提交到其他客户端可见的延迟、断网恢复到追平的时间、快照回退率、同步失败率、幂等重试及版本冲突数。Java、Rust 使用相同的快照、事务、删除、命令结果与故障恢复契约用例。上线评审需确定快照和日志保留窗口、业务查重规则、是否开放离线编辑，以及根据压测制定的延迟预算。
