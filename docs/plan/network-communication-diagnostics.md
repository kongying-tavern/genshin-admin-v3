# 「设置 → 网络」通信诊断实施计划

把「日志」替换为「通信诊断」。用户打开设置能看到连接现状，点开一条历史记录能看到消息最后到了哪里、哪一步出了问题。「响应时延」显示最近一次有效检测的实测值和测量时间。实施沿用现有 Socket.IO 服务、页面与 Worker 的通信通道，以及本地 IndexedDB。

## 用户如何回看一次通信

- 收起时显示连接状态、最近检测时间及最近异常摘要。连接恢复后显示恢复时间，仍可点开当时的记录。
- 展开后固定显示「当前页面」「浏览器后台」「服务器」三列。每行代表一步，从上到下按发生顺序排列。实线箭头表示接收端已有凭据，虚线表示已尝试发送、送达待确认。把超时或失败标在实际等待或处理的位置，并写明原因。
- 「最近往来」用「连接检测」「点位更新」等中文名称。连续成功的例行检测合并显示次数和最近结果，异常单独保留。默认选中最近异常，没有异常时选中最新记录。用户回看期间，新记录到达只更新列表。

以「更新通知已到，点位详情读取失败」为例。服务器到后台、后台到本页的两条箭头都显示成功，失败标记落在「当前页面」列的「读取点位详情」这一步。如果后台发起连接检测后一直等不到回复，则在「浏览器后台」列标出「等待服务器回复超时」，服务器一端显示「是否收到待确认」。

## 实施顺序

### 一、建立可以回看的通信记录

当前 Worker 把收到的消息原文写入 `websocket.logs`，设置面板每次读取全表并截取最后十条。旧记录只有时间、消息和级别，三列图的历史从新版采集启用时开始。[数据库定义](../../src/database/websocket/index.ts) · [网络设置面板](../../src/components/AppSettings/modules/ModuleNetwork.vue)

| 一条记录需要的信息 | 用途 |
| --- | --- |
| 通信编号、连接实例编号、所属账号、事件种类 | 一次远端检测复用 `rttcheck.id`。一次推送由 Worker 在收到原始消息时分配编号，同类事件并发也能分别回看。每次实际重连分配新的连接实例编号。 |
| 步骤、发起方、接收方、观察时间、结果 | 区分已发起、已接收、处理中、已完成、超时、失败和中断。用步骤间的先后关系排图，本地时间用于显示，服务端时间戳仅用于计算服务端耗时。 |
| 页面编号、失败步骤、原因类别、检测样本、恢复时间 | 共享连接的收发只记录一次。每个标签页分别记录自己的接收和处理结果。回看优先展示本页分支，历史摘要注明异常发生在哪一次页面会话。 |

在现有 `websocket` Dexie 库的下一版新增诊断表。Worker 写连接和收发步骤，页面写本页接收、业务处理及本地等待结果。按通信编号、页面编号和步骤标识，在读写事务中合并增量。同一步骤的重复回执只计一次，迟到的证据追加至原轮次。只保存上述诊断字段，原始业务负载留在业务处理路径。

按账号、时间及是否异常建索引，面板通过 `liveQuery` 分页读取。首版建议每个账号保留最近 100 条普通记录和 50 条异常记录，记录结束时才计入上限。任一页面分支发生异常，整次往来进入异常保留范围。设置面板关闭期间照常采集，刷新后仍可按原事件时间回看。

升级时保留旧日志表里的历史数据，新版停止写入原文。诊断存储写入失败时，业务分发继续，面板提示「本次记录可能不完整」。状态栏的业务事件历史有独立的 `db.websocketEvents` 表。[业务事件历史的读写入口](../../src/stores/socket/hooks/useMessageList.ts)

### 二、接入页面、后台和服务器的真实连接状态

| 观察位置 | 何时记一步 | 如何归因 |
| --- | --- | --- |
| 当前页面 → 浏览器后台 | 页面创建 Worker 前分配本次接入编号并计时，收到 `init` 后关联后台分配的页面编号。创建报错或等待初始化超时，由本页记录。 | 「本页未能启动连接后台」或「等待浏览器后台回应超时」。账号尚未就绪的步骤先留在本页，身份确定后归档。 |
| 浏览器后台 ⇄ 当前页面 | 现有本地心跳由 Worker 每轮等待 10 秒后发 `ping`，页面有 10 秒回 `pong`。按端口确认最近一次回应，本地心跳连续成功时合并。 | 标签页长时间未回应时标记该页。挂起页面恢复时重新确认端口，正常关闭时记为结束。服务器检测独立进行。 |
| 浏览器后台 ⇄ 服务器 | 记录 Socket.IO 的 `connect`、`connect_error`、`disconnect` 及重新连接。真实连接建立后才开始远端检测。 | 分别显示「正在连接」「建立连接失败」「连接中断」。主动退出记为「连接已结束」。同一段链路再次得到确认后才记录恢复时间。 |

让 SharedWorker 和普通 Worker 共用连接、端口处理及诊断逻辑。当前普通 Worker 分支只发送初始化状态，需接通 `open`、`close`、心跳和消息转交。复用时核对所属账号和 socket 的实际连接状态。建连失败后释放对应的 `openPromise`，底层正在重连时让新端口加入已有连接。两个标签页共用一个连接时只启动一套远端检测。把本地接入和远端建连分别记录，`open` 尚未返回时也能看出正在等哪一段。[Worker 入口](../../src/worker/webSocket/socket.worker.ts) · [页面连接入口](../../src/stores/socket/hooks/useSocket.ts) · [登录和退出时的连接调用](../../src/stores/socket/index.ts)

### 三、测量响应时延，并在漏回包后继续检测

1. 把远端检测间隔和回复时限集中到连接配置。现有面板引用的 15 秒来自另一项心跳配置，实际远端检测在成功回包 30 秒后才发起下一次。首版建议连接成功立即测一次，每轮结束 30 秒后再测，等待回复上限先取 10 秒。面板提示读取同一配置。本地端口心跳沿用其独立的计时。[连接配置](../../src/configs/websocket.ts) · [现有检测循环](../../src/worker/webSocket/socket.worker.ts)
2. 每条已连接的 socket 同时只保留一次待回复检测。用 Worker 内的单调时钟记录发起和收到匹配回包的时刻。只有当前连接在时限内首次收到的匹配回包能生成当前样本。成功和超时都安排下一轮。断开、切换账号或替换连接时清理等待和调度定时器，结束旧记录。
3. **面板主值采用网络往返耗时。** 同一 Worker 测得的收发差值是检测总用时。服务器处理耗时取回包中的 `sendTimestamp − receiveTimestamp`。总用时减去服务器处理耗时，就是展示值。例如总用时 46 ms、服务器处理 4 ms，面板显示 **42 ms**，展开记录可见三个数。两个差值分别来自同一端的时钟。[回包类型](../../types/socket.d.ts)
4. 通过 Worker 到页面的 IPC 下发检测编号、连接实例、测量时间及结果，在页面接收回调记下「检测结果已到本页」。刚加入共享连接的标签页读取该连接最近一次样本及其原测量时间。用空样本替换页面初值 0 和 Worker 初值 999。状态栏消费处适配空样本，有效值沿用其展示规则。[页面时延状态](../../src/stores/socket/hooks/useSocket.ts) · [状态栏时延消费者](../../src/components/AppStateBar/components/WebSocketStatus/WebSocketStatus.vue)
5. 设置面板直接显示实测毫秒数。首次回包前显示「待测」，本轮超时显示「本次检测超时」，断开时显示「未连接」。上次成功值带时间单列。服务器时间缺失、非有限、倒序或处理耗时超过总用时时，仍能确认「已收到回复」及本地总用时，网络往返值显示「暂无有效样本」。

### 四、把推送送达和页面处理串成同一条记录

1. Worker 在 Socket.IO 的 `message` 回调入口记录「后台收到推送」，再记录解析结果。遇到格式错误，异常落在后台的「读取通知内容」。识别出业务事件后向各端口转交，在 IPC 消息外层附上通信编号及连接实例编号。保留原有业务参数和订阅方式，现有进程间请求编号继续用于匹配调用返回。[IPC 消息结构](../../src/utils/worker/types.ts) · [后台发送入口](../../src/utils/worker/worker-ipc.ts)
2. 页面收到带编号的消息时，在本页记一次接收并回传页面编号与通信编号。后台的 `postMessage` 产生「已转交」步骤，有本页接收记录或对应回执才画实线。如果本页已记接收、后台却等回执超时，图上同时显示「通知已到本页」和「后台等待页面确认超时」。诊断回执只更新原记录。[页面接收入口](../../src/utils/worker/page-ipc.ts)
3. 将同一个编号传入实际业务处理回调。以 `MarkerUpdated` 为例，在 `listMarkerById` 调用前记「读取点位详情」，返回后分别记录已取得详情、未找到点位或请求失败，分发成功后记「已交给页面处理」。按同一方式覆盖实际有后续查询的点位、关联、物品等处理分支。仅转发的通知在实际分发处结束，纯本地事件沿用本地来源。每一步复用已有请求和结果。[业务处理分支](../../src/stores/socket/hooks/useAppEvent.ts) · [事件来源定义](../../src/api/ws/typings.d.ts)
4. 一次通信保留最初的异常和最后已确认的步骤。后一次远端检测成功可结束同一连接中连续的回复超时，多次重连后的首次成功可标记该次断连已恢复。某条推送的详情读取失败仍保留在它自己的记录里。页面或 Worker 意外结束后，已失效会话中尚未收尾的记录显示「过程中断，后续待确认」。

### 五、替换设置面板的日志区域

复用设置分组和折叠样式，将「日志」、原始 JSON 导出和清空日志入口替换为连接概况、三列时序图及最近往来列表。组件只读取记录与检测样本，打开面板即能回看此前的通信。初次启用显示「等待首次通信」。正常检测、超时和失败同时用文字、图标和线型区分。窄屏保留列名及箭头方向，可用键盘展开和选择记录。通知开关、事件勾选和状态栏业务历史分别走原有入口。[网络设置](../../src/components/AppSettings/modules/ModuleNetwork.vue) · [设置折叠组件](../../src/components/AppSettings/components/SettingBar.vue)

## 实施验收

| 场景与操作 | 可验证的结果 |
| --- | --- |
| 首次连接，随后收到同编号回包 | 先显示「待测」。总用时 46 ms、服务器处理 4 ms 的样本得到 42 ms。跨端时钟有固定偏差时仍得到相同结果，实测超过 999 ms 时设置面板显示完整数值。异常时间戳只影响耗时分解。 |
| 让一次远端检测收不到回包，再恢复回复 | 异常停在后台的「等待服务器回复」步骤。下一轮仍会发起，新回包恢复概况并保留前次异常及时间。补到的旧回包不会刷新当前时延。 |
| 页面接入没有回应，或服务器建连失败 | 前者停在页面等待后台，后者显示后台已接入、正在建立远端连接时失败。普通 Worker 后备路径也能观察到真实连接、回包和推送。 |
| 在联调环境触发点位更新，再分别让详情请求失败和返回空结果 | 两条送达箭头都有接收证据。末步分别显示「读取点位详情失败」和「未找到点位」。同类型推送并发或返回顺序颠倒时，各自步骤仍对应原消息。 |
| 向测试接收器提供格式错误的消息，随后交付正常推送 | 前一条记录停在后台的「读取通知内容」，后一条能独立送达页面。 |
| 两个标签页共用连接，让一个页面延迟确认，然后断开重连 | 只产生一轮远端检测，各页有自己的接收结果。新连接只采用自己的回包，旧定时器结束，成功的页面分支仍显示成功。 |
| 关闭设置期间发生连接异常，随后恢复、刷新、再打开 | 可以找到原记录和恢复时间。连续正常检测合并后，最近异常仍可选中。切换账号后只读取该账号历史，查看旧记录时选中项保持稳定。 |
| 从含旧日志的数据库升级，再开关通知并查看状态栏事件 | 新表可读写，旧数据可保留。通知偏好和业务事件历史各自正常工作，关闭弹窗通知后仍会采集诊断步骤。 |
| 缩窄设置窗口到 320 像素，用键盘展开并切换历史记录 | 三列名称、箭头方向和失败步骤可读。选中状态清晰，诊断结论可以通过文字读出。 |

实施完成时运行仓库已有的 `pnpm typecheck`、`pnpm lint` 和 `pnpm build`。实际联调用一次真实 `rttcheck` 回包和一次真实点位推送核对图上的步骤，可控时钟和回包样本用于复核超时、迟到及数值边界。[项目脚本](../../package.json)
